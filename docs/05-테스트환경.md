# 테스트 환경

빌드 → 부팅 → 디버그 사이클의 길이가 개발 속도를 결정한다. 이 문서는 **반복 사이클을 5~10초로 유지하는 환경 셋업**.

---

## 1. 환경 비교 (요약)

| 도구 | 부팅 속도 | 디버그 | 결정성 | 용도 |
|------|----------|--------|--------|------|
| **QEMU/TCG** | 5~10초 | GDB stub | 결정적 | ★ 일상 (주력) |
| **QEMU+WHPX** | 1~3초 | GDB 일부 제약 | 약간 비결정 | 후기 단계 가속 |
| **Bochs** | 30~60초 | 명령 단위 추적 | 가장 결정적 | 초기 부팅 버그 |
| **VirtualBox** | 5~10초 | 약함 | 결정적 | GUI 데모용 (선택) |
| **실기 USB** | 1~3분 | 시리얼만 | 비결정 | 분기 1회 검증 |

**기본 권장**: QEMU/TCG 주력 + Bochs 보조 + 분기 1회 미니 PC. WHPX는 페이즈 3 이후 가속이 필요해질 때.

---

## 2. QEMU 설치 (Windows 호스트)

### 2-1. 설치

공식 빌드: `https://www.qemu.org/download/#windows`

또는 패키지 매니저:
```powershell
# winget
winget install qemu.qemu

# chocolatey
choco install qemu

# scoop
scoop install qemu
```

### 2-2. 설치 확인

```powershell
qemu-system-x86_64 --version
```

### 2-3. WHPX (선택, 후기 단계용)

WHPX는 Windows Hypervisor Platform. 활성화하면 QEMU가 KVM급 속도를 냄.

- Windows 10/11 Pro·Enterprise·Education 필요 (Home은 안 됨)
- 기능 추가/제거 → **Windows Hypervisor Platform** 체크
- 재부팅 후 QEMU 실행 시 `-accel whpx` 옵션
- 충돌 가능성: VirtualBox와 동시 사용 시 한쪽이 가속 못 받음

페이즈 0~2에는 TCG로 충분. WHPX는 SIP 다수 띄울 때 (페이즈 3) 검토.

## 3. 표준 QEMU 실행 명령

### 3-1. 기본 부팅

```powershell
qemu-system-x86_64 `
  -kernel build/kernel.elf `
  -serial stdio `
  -m 256M `
  -no-reboot -no-shutdown
```

옵션 의미:
- `-kernel`: Multiboot2 호환 ELF 직접 로드 (GRUB 없이도 됨)
- `-serial stdio`: 시리얼 포트 → 호스트 stdout. 글 OS의 디버그 출력 채널
- `-m 256M`: 게스트 RAM (페이즈 0~2 충분, 후기 1G로 확장)
- `-no-reboot -no-shutdown`: 트리플 폴트 시 무한 재부팅 방지 — **디버그 핵심**

### 3-2. GDB 원격 디버그

```powershell
qemu-system-x86_64 -kernel build/kernel.elf -s -S -serial stdio
```

- `-s`: GDB 서버 포트 1234 오픈
- `-S`: 부팅 즉시 정지, GDB 연결 기다림

다른 터미널에서:
```powershell
gdb build/kernel.elf
(gdb) target remote :1234
(gdb) break 커널진입         # 글 함수 이름 그대로 사용 가능 (DWARF 심볼 등록 후)
(gdb) continue
```

DWARF 디버그 심볼 emit은 페이즈 0의 작업 항목.

### 3-3. 자동화 (CI용)

`isa-debug-exit` 디바이스 활용:

```powershell
qemu-system-x86_64 `
  -kernel build/kernel.elf `
  -device isa-debug-exit,iobase=0xf4,iosize=0x04 `
  -display none -serial stdio -no-reboot
```

게스트가 포트 0xF4에 종료 코드를 쓰면 QEMU 종료 → 호스트 프로세스의 exit code로 전달.

```글
(* 게스트 측 *)
[정수 종료코드를 OS종료]은 {
    포트출력_4바이트(0xF4, 종료코드).
}
```

페이즈 1부터 회귀 테스트가 부팅 단위로 돌 수 있음.

## 4. Bochs 설치와 사용

긴 부팅·페이지 테이블·long mode 전환 같은 어려운 버그 잡을 때.

### 4-1. 설치

`https://bochs.sourceforge.io/` Windows 인스톨러.

또는:
```powershell
winget install Bochs.Bochs
```

### 4-2. bochsrc 예시

```
megs: 256
romimage: file=$BXSHARE/BIOS-bochs-latest
vgaromimage: file=$BXSHARE/VGABIOS-lgpl-latest
boot: disk
ata0-master: type=disk, path="glos.img", mode=flat
log: bochs.log
panic: action=ask
error: action=report
info: action=report
debug: action=ignore
display_library: win32
magic_break: enabled=1
```

`magic_break`: 게스트에서 `xchg bx, bx` 명령이 Bochs 디버거에 정지점 트리거. 인라인 어셈블리로 쉽게 박을 수 있음.

### 4-3. 결정성

같은 입력 → 항상 같은 명령 시퀀스. QEMU는 호스트 인터럽트 영향으로 미세한 비결정성 있음. Bochs는 명령 0번부터 끝까지 동일.

## 5. 빌드 → 부팅 사이클 (목표)

```
글 소스 변경
   ↓ (글 컴파일러, --freestanding --멀티부트2)
build/kernel.elf
   ↓ (QEMU)
부팅 + 실행
   ↓ (시리얼)
호스트 콘솔에 로그
```

목표 사이클 시간: **5~10초**. 더 길면 디버그 패턴이 무너짐.

### 5-1. Makefile 또는 빌드 스크립트

페이즈 0의 작업 항목. 글 빌드 → ELF → QEMU 한 명령으로 실행되어야 함.

```powershell
# 예시 (페이즈 0에서 작성)
.\build.ps1                # 빌드만
.\build.ps1 run            # 빌드 + QEMU
.\build.ps1 debug          # 빌드 + QEMU -s -S
.\build.ps1 bochs          # 빌드 + Bochs
.\build.ps1 test           # 빌드 + QEMU 자동 종료 + exit code
```

## 6. 디버그 출력 채널

### 6-1. 시리얼 포트 (COM1 = 0x3F8)

가장 신뢰성 높음. 인터럽트 없이도 동작. **페이즈 0 spike 1순위**.

```글
(* 의사 코드 — 페이즈 0~1에서 구현 *)
[문자열 메시지를 시리얼출력]은 {
    (* 메시지[i] 가 0이 아닐 때까지 *)
    (* 포트출력바이트(0x3F8, 메시지[i]) *)
}
```

QEMU `-serial stdio` 와 결합 시 호스트 콘솔에 직접 출력.

### 6-2. VGA 텍스트 (0xB8000)

화면에 직접 쓰기. 페이즈 1에서 작성. 사용자 가시.

### 6-3. QEMU 디버그콘 (0xE9)

QEMU 전용 디버그 콘솔. `-debugcon stdio` 옵션. 초기 부팅의 단순 디버그용.

## 7. 실기 부팅 (분기 1회 검증)

### 7-1. 권장 하드웨어

- 중고 미니 PC (Intel NUC 구형, AMD 미니 PC 등 — 20~30만 원대)
- UEFI 부팅 가능 (또는 레거시 BIOS도 OK)
- 시리얼 포트 또는 USB-to-Serial 어댑터
- **본 PC와 별도** — 본 PC 위험 없음

### 7-2. USB 이미지 생성

```powershell
# 페이즈 4 이후에 정의될 절차
# 1. 글 OS 이미지 빌드 (multiboot2 + GRUB 또는 자체 부트로더)
# 2. dd 또는 Rufus로 USB에 굽기
# 3. 미니 PC 부팅
```

상세 절차는 페이즈 4에서 정의.

### 7-3. 시리얼 콘솔

```
[글 OS 게스트 PC] --- USB-Serial --- [개발 PC, 시리얼 터미널]
```

PuTTY, Tera Term, screen 등으로 모니터링. 화면 출력은 게스트 모니터에, 디버그는 시리얼로.

## 8. 디버그 워크플로 (페이즈 1 이후)

### 8-1. 일상 패턴

1. 글 소스 편집 (호스트 Windows의 VSCode)
2. `.\build.ps1 run` — 5~10초
3. QEMU 창과 호스트 콘솔 동시 관찰
4. 잘 안 되면 `.\build.ps1 debug` 로 GDB 붙임
5. 명령 단위 추적 필요 시 `.\build.ps1 bochs`

### 8-2. 트리플 폴트 디버그

증상: QEMU가 계속 재부팅, 아무것도 안 보임.

대응:
1. `-no-reboot -no-shutdown` 추가됐는지 확인 (디폴트 셋업에 있어야 함)
2. `-d int,cpu_reset` 추가 → 인터럽트/리셋 로그
3. 그래도 안 되면 Bochs로 옮겨서 명령 단위 추적

### 8-3. 무한 루프 / 정지

증상: QEMU가 멈춘 듯, 진행 없음.

대응:
1. `Ctrl+a c` (QEMU 모니터) 또는 `-monitor stdio` 옵션
2. 모니터에서 `info registers` — 현재 RIP 확인
3. `x/10i $rip` — 어디서 멈췄는지
