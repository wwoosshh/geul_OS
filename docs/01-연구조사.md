# 연구조사

글 OS 설계의 출발점이 된 외부 사례, 학술 연구, 기존 OS의 누적된 한계 정리. 이 문서는 **영감의 출처 카탈로그**이며, 채택 결정은 `02-아키텍처비전.md`에서 한다.

---

## 1. 기존 OS의 누적된 한계 (왜 새로 만드는가)

### 1-1. POSIX/Win32라는 50년 화석

- **fork()** (1970, PDP-7): exec 직전 fork는 페이지 테이블 COW 복제 낭비. NT 커널이 30년째 흉내내려 고생 중
- **signal**: 비동기 처리 부적합하지만 호환성으로 못 버림. signal-safe 함수 목록 암기 필요
- **errno**: 전역 변수 한 개로 에러 전달. 스레드 등장 후 TLS로 가짜 전역화
- **Win32**: 1985년 16비트 시그니처 (`WPARAM`/`LPARAM`)가 아직 살아있음

### 1-2. 파일시스템 계층의 의미 상실

- `/usr/local/bin` vs `/opt` vs `/usr/bin`: 1970년대 디스크 분할 정책 잔재
- Windows: `C:\Program Files`, `Program Files (x86)`, `ProgramData`, `%APPDATA%`, `%LOCALAPPDATA%`, 레지스트리 4곳, `WinSxS` — 같은 정보 6~7군데
- **숨김 파일 `.`**: Ken Thompson이 `ls` 작성 시 `.`/`..` 만 거르려다 실수로 점-시작 모두 거른 게 50년 관습

### 1-3. 보안 모델의 누더기

- Unix: DAC → ACL → capabilities → SELinux/AppArmor → systemd 권한 → ...
- Windows: ACL → UAC → Integrity Levels → AppContainer → ...
- 같은 개념을 4~5개 메커니즘이 중첩으로 표현 → 일관성 0, 감사 불가

### 1-4. 드라이버 = 커널 폭탄

- Windows BSOD 70%+ 가 서드파티 드라이버 (Microsoft 자체 통계)
- 커널에 코드 주입을 허용하는 구조 자체가 결함. CrowdStrike 사건(2024)이 단적 예
- 리눅스도 같은 구조, 차이는 트리 검토뿐

### 1-5. 부팅 레이어 무한 적층

BIOS → UEFI → bootloader 1단계 → 2단계 → 커널 → initrd → systemd → display manager → session → ...

각 레이어가 다른 시대 가정으로 만들어져 변환 비용이 누적. Windows 11 부팅이 XP보다 느린 이유.

### 1-6. Windows 11이 더 느려진 진짜 이유 (사용자 평가의 구조적 근거)

- TPM 2.0 강제로 모든 디스크 I/O에 암호화 계층
- Defender + EDR + SmartScreen + Application Guard가 같은 파일을 4번 스캔
- Edge 백그라운드 사전 로드 (4년째 못 빼는 디폴트)
- Cortana·검색 인덱싱이 SSD 마모 가속
- DirectStorage, WinUI, MAUI, WPF, WinForms — GUI 스택 5개 병존
- 각각이 독립 팀의 산물, 디프리케이션 불가

> **결론**: "발견 안 된 문제"가 아니라 "버릴 수 없는 호환성 부담". 새 OS의 단 하나 결정적 강점은 그 부담이 0이라는 것.

## 2. 영감의 원천 — 학술·산업 OS

### 2-1. Singularity (Microsoft Research, 2003~2008) ★★★

- **핵심**: Software Isolated Process (SIP). 컴파일러(Sing#, C# 확장)가 메모리/타입 안전성 보장 → MMU 격리 없이 프로세스 격리
- **결과**: 컨텍스트 스위치가 함수 호출 수준 (TLB flush 없음)
- **메시지 패싱**: 채널 기반 IPC, 채널 계약은 컴파일 타임 검증
- **글 OS와의 매핑**: 글 컴파일러를 직접 통제 가능, C/C++ 같은 unsafe 언어를 지원할 의무 없음 → **가장 직접적인 모델**
- **참고**: Galen Hunt et al., "Singularity: Rethinking the Software Stack" (ACM SIGOPS 2007)

### 2-2. Theseus OS (Rice University, 2017~) ★★★

- Singularity의 정신적 후예. Rust로 구현
- **Intralingual OS**: 메모리 관리·동기화·스케줄링까지 모두 언어 타입 시스템으로 표현
- 라이브 진화(live evolution): 커널 모듈을 실행 중 교체 가능
- **글 OS와의 매핑**: Singularity보다 현대적이고 단순한 청사진. 한 명이 따라가기에 더 현실적
- **참고**: Kevin Boos, "Theseus: a State Spill-free Operating System" (HotOS 2017, OSDI 2020)

### 2-3. seL4 (NICTA/Data61, 2009~) ★★★

- 형식 검증된 마이크로커널 (functional correctness 증명됨)
- **능력 기반 보안**: 모든 권한이 capability. 능력 없는 호출은 구조적으로 불가능
- 매우 작은 커널 (10k LoC 수준), 드라이버 등 모든 것 user space
- **글 OS와의 매핑**: 능력 모델 채택. 다만 형식 검증은 폴백 옵션(과한 야망)
- **참고**: Gerwin Klein et al., "seL4: Formal Verification of an OS Kernel" (SOSP 2009)

### 2-4. KeyKOS / EROS (1980~2000) ★★

- **영속 메모리 모델**: 5분마다 체크포인트, 시스템 상태 항상 디스크 복원 가능
- 사용자 관점: 종료/재부팅이 의미 없음
- 능력 기반 보안의 원형
- **글 OS와의 매핑**: 영속 모델 채택. 현대 NVMe·PMEM과 더 잘 맞음
- **참고**: Norman Hardy, "KeyKOS Architecture" (ACM SIGOPS 1985)

### 2-5. L4 계열 (Liedtke 1995~ / OKL4 / Fiasco / seL4) ★★★

- 마이크로커널 + 동기 메시지 IPC가 함수 호출에 근접하는 성능 입증
- "최소 메커니즘" 철학: 커널은 IPC·스케줄·메모리 격리만, 나머지는 user
- **글 OS와의 매핑**: 동기 메시지 패싱 IPC 채택. 다만 글 OS는 단일 주소공간이라 메시지 = 포인터 전달

### 2-6. Plan 9 / Inferno (Bell Labs, 1992~) ★★

- **"모든 것은 파일"** 을 진짜로 구현 (네트워크 카드·GPU·다른 프로세스 메모리까지)
- 9P 프로토콜 통일성
- **per-process 네임스페이스**: mount/bind가 가볍고 사용자별
- **글 OS와의 매핑**: 부분 채택. 통일성 정신은 좋지만 도그마틱한 부분은 거름
- **참고**: Rob Pike et al., "Plan 9 from Bell Labs" (Computing Systems 1995)

### 2-7. TempleOS (Terry Davis, 2003~2017) ★★★

- 한 명이 자체 언어(HolyC) + 자체 컴파일러 + 자체 OS 모두 작성
- **글 OS의 가장 직접적인 비교 사례**
- 의도적 제약: 640×480, 16색, 단일 사용자, 모든 코드 ring 0, 멀티프로세스 협력적
- **취한 것**: 작가성, 셸=언어 동일, 의도적 비-호환
- **거를 것**: 보안 의식 0, 멀티태스킹 한계, 모든 코드 ring 0

### 2-8. Mungi / Opal (1990년대) ★

- **단일 주소공간 OS** (SASOS): 64비트 한 공간에 모든 프로세스 공존
- 격리는 능력으로, 메모리 보호는 페이지 권한 비트로
- IPC = 단순 포인터 전달
- **글 OS와의 매핑**: 단일 주소공간 채택. 다만 보호는 컴파일러로(Singularity 식)

### 2-9. Hubris / Oxide Computer (2021~) ★

- Rust 기반 작은 임베디드 RTOS
- 태스크가 컴파일 타임에 고정 (런타임 동적 spawn 없음)
- IPC가 시스템의 중심
- **시사점**: "동적성을 줄이면 검증과 격리가 쉬워진다"

### 2-10. Redox OS (2015~) ★

- Rust 기반, 마이크로커널, POSIX 부분 호환
- **거를 것**: POSIX 부분 호환 시도 → 우리는 비-목표

## 3. 한국어 단일성을 OS에서 활용하기 (참고 자료가 거의 없는 영역)

선례가 없는 영역이라 추론으로 정리.

### 3-1. 인코딩 통일

- Windows의 CP949(EUC-KR) ↔ UTF-8 ↔ UTF-16 ↔ ACP 변환은 시스템 전반에 매장
- macOS의 UTF-8 NFD/NFC 정규화 차이로 한글 파일명 충돌
- **글 OS는 내부 UTF-8 단일**. 변환 코드 0줄. 로케일 협상 폐기

### 3-2. 셸 = 언어

- TempleOS의 HolyC 모델이 증명: 셸이 언어 자체일 때 OS 전체가 통일된 정적 분석 가능
- 글 SOV 어순이 명령 구조와 자연 매핑: `이파일을 저폴더에 복사하기.`

### 3-3. 시스템 콜 = 글 함수

- 메뉴얼 페이지 = 함수 시그니처. `man read` 같은 별도 문서 불필요
- 조사 시스템 덕에 영문 시그니처보다 가독성 ↑
  - C: `read(fd, buf, count)`
  - 글: `[파일에서 버퍼로 길이만큼 읽기]는 -> 정수`

### 3-4. 에러 한국어 1차 시민

- "오류: '%s' 인자가 중복됩니다" 같은 메시지가 OS 전체 일관

### 3-5. 한글 자료구조 명명

- `프로세스기술자`, `페이지테이블엔트리`, `인터럽트게이트` — 한국어 자체로 자료구조 표현
- **단**: 글 렉서의 한글 식별자/조사 충돌 이슈가 폭증할 영역 → 페이즈 0의 1주차 작업

## 4. 현대 하드웨어 기능 (기존 OS가 디폴트 활용 안 하는 것)

글 OS는 디폴트로 깔고 시작.

| 기능 | 활용처 |
|---|---|
| **Intel MPK (Memory Protection Keys)** | SIP 내부 라이브러리 격리 (16개 도메인) |
| **Intel CET (Shadow Stack + IBT)** | ROP/JOP 방어, 컴파일러가 의식하면 무료 |
| **PCID/ASID** | TLB 태깅, 컨텍스트 스위치 시 flush 회피 |
| **NX-only / W^X** | 코드 영역이 데이터로 안 쓰이게 |
| **SMAP/SMEP** | 커널 코드가 사용자 메모리 접근/실행 방지 |
| **AMD SEV / Intel TDX** | 메모리 암호화 (디스크 덤프 방어) |
| **x2APIC** | 인터럽트 처리 개선 |
| **5-level paging** | 128 PiB 주소공간 (단일 주소공간 OS에 유리) |

## 5. 테스트·개발 환경 사례

### 5-1. QEMU + GDB

- 표준 hobby OS 환경. `-s -S` 로 부팅 즉시 정지 → gdb 원격 접속
- `isa-debug-exit` (포트 0xF4)로 게스트→호스트 종료 코드 전달, CI 자동화 가능
- WHPX/KVM 가속 옵션, TCG 순수 SW 폴백

### 5-2. Bochs

- 명령 단위 추적, 가장 결정적. long mode 전환·페이지 테이블 버그 잡을 때 강력
- 느림 (QEMU 대비 10~50배)

### 5-3. 실기 부팅 (USB)

- 최종 검증. 중고 미니 PC + 시리얼 콘솔이 정석

## 6. 참고할 가치가 있는 책·자료

- **OSDev Wiki** (`wiki.osdev.org`): hobby OS의 사실상 표준 백과사전

- **AMD64 Architecture Programmer's Manual**: AMD 측 동치

- *Operating Systems: Design and Implementation* (Tanenbaum, MINIX 책)
- *The Design and Implementation of the FreeBSD Operating System* — BSD 계열 깊이
