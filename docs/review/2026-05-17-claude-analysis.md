## 0. 한 줄 결론

> GeulOS는 *비전·설계·문서화 측면에서 학회 수준*이지만, *솔로 개발자 일정·글 언어 의존성·포지셔닝 약점* 세 가지가 잠재적 실패 요인이다. 시장 진입 윈도우는 약 1.5~2년 (Apple/MCP가 AI-네이티브 OS 내러티브를 장악하기 전).

## 1. 일정·실행 리스크

### 1.1 11개월 MVP는 비현실적

**상황:** §9.4의 누적 일정은 *풀타임 단독 개발자 + AI 보조* 기준의 "낙관적" 추정 (본인 명시).

**문제:**
- 솔로 OS 프로젝트는 일정이 평균 2~3배 늘어남 (Redox, Haiku, SerenityOS 사례)
- M5(글 AI 드라이버)가 글 언어 측 G1~G4 *완료에 직렬 의존* → 두 거대 프로젝트가 일정 면에서 묶임
- 파트타임 진행 시 §9.4 본문 그대로 1.5~2배 → **현실적 MVP 일정은 18~24개월**

**유의:**
- 외부 약속(블로그, 데모 영상, 컨퍼런스 발표)에 *MVP 날짜*를 박지 말 것
- 대신 작은 마일스톤(M2 데모, M4 컴포지터 영상)을 약속 단위로 쓸 것

### 1.2 솔로 개발자 SPOF

**문제:** 모든 마일스톤이 본인 한 명에 의존. 한 달 멈추면 한 달 전체가 멈춤.

**유의:**
- M1·M2 완료 후, 핵심 차별점이 명확해진 시점에서 *최소 1명의 협업자 모집* 검토
- 협업자 영입 전에 ADR/Plan 영문화 필요 (한국어 문서로는 글로벌 협업자 못 들어옴)

### 1.3 M5 plan 부재 (현재는 M4 작업 중이라 OK)

**현재 상태:** M4 작업 중이라 M5 plan이 아직 없는 것은 *정상* (본인 확인 2026-05-17).

**유의:**
- M4 완료 시점에 *M5 plan을 작성*해야 함. M5는 글 VM 임베드 + AI 자연어 해석으로 *가장 어려운 마일스톤*
- M5 작업 시작 전에 글 언어 측 G1~G3가 *최소 임시 형태로라도* 동작해야 함
- 만약 G 시리즈가 지연되면 M5의 "모의 글 VM 우회" 경로 (§9.6 리스크 표) 발동 결정 필요

## 2. 기술적 부채와 설계 일관성

### 2.1 M3의 ACL Wildcard — 보안 모델 우회

**상황:** M3 plan Task 8에서 echo-app acceptance를 통과시키기 위해 `build_ui`에서 button에 wildcard ACL을 추가하기로 결정.

**문제:**
- §7의 정교한 보안 모델(신뢰 영역 T0~T5, 보안 불변식 S1~S6)과 *직접 충돌*
- "내 버튼은 누구나 누를 수 있다"는 *앱이 명시적으로 자기 보안을 약화*시키는 패턴 — Android의 `exported=true` 실수와 동일한 함정

**유의:**
- M4(컴포지터)에서 "사용자 동의 다이얼로그" 도입 시 wildcard ACL을 *즉시 제거*하고 명시적 권한 부여로 교체할 것
- M3 acceptance를 통과시키기 위한 *임시 조치*임을 ADR 또는 코드 주석으로 명시 (현재 ADR-012 시드만 있고 본문 없음)
- 보안 부채는 빠르게 누적되므로, M4 완료 전 *별도 보안 회귀 테스트*로 wildcard 잔존 여부 검출

### 2.2 Toolchain Bump가 의미하는 것

**상황:** Rust 1.78 → 1.85 점프 + uuid/proptest/toml 핀 해제 + hand-rolled TOML parser 교체.

**문제:**
- 1.78에 갇혀 있었던 18개월 = *기술 부채가 무음으로 누적*된 기간
- 핀이 3개 누적된 후에야 정리 — *반응적* 부채 관리

**유의:**
- 향후 의존성 핀이 *2개* 누적되면 즉시 toolchain/dependency 점검 (선제적 패턴)
- 의존성 핀 추가 시 ADR 또는 `KNOWN-ISSUES.md`에 *왜 핀했는지* 기록 → 핀 해제 시점 판단 가능

### 2.3 단일 라이터 이벤트 루프의 진짜 가치 미강조

**상황:** ADR-003에서 단일 라이터 채택. 부수 효과로 "무료 매크로/녹화/undo + 결정론적 리플레이"를 얻음.

**문제:**
- 이게 GeulOS의 *진짜 차별점*인데 README/외부 자료에서 강하게 부각되지 않음
- Apple App Intents도, MCP도, AIOS도 *이 부수 효과를 제공 못 함* — 단일 라이터 이벤트 루프는 OS 차원에서만 가능
- "AI에게 점자 설명서" 비유보다 *"OS 1급 시간 여행"* 이 마케팅적으로 더 강력

**유의:**
- 영문 README 첫 화면에 "Free macro/undo/replay — built into the OS, not bolted on" 같은 차별점 명시
- 데모 영상에 *"AI가 한 작업을 사용자가 한 번 클릭으로 undo"* 시나리오 포함

## 3. 글 언어 관련 리스크와 포지셔닝 재정립

### 3.1 글 언어의 정당화 논거가 약함

**현재 본인 논거:** "SOV 자연어 문법이 LLM에 추상화하기 좋다"

**문제:**
- 현대 LLM(Claude 4.7, GPT-5)은 구조화 출력(JSON/Python/JS)이 자연어만큼 또는 *더* 정확
- 한국어식 SOV는 LLM 토큰 효율 *불리* (한국어 1단어 ≈ 2~4토큰, 영어/코드 ≈ 1토큰)
- HumanEval-Korean 등 벤치마크에서 한국어 코드 생성 < 영어 코드 생성 정확도

**유의:**
- "LLM이 자연어 좋아한다" 논거는 *2022~2023년 GPT-3.5 시절의 가설*. 2026년에는 약함
- 글 언어를 *기술적 LLM 친화성*으로 정당화하지 말 것

### 3.2 글 언어의 진짜 가치 — 재정립 필요

**더 강력한 정당화:**

1. **사람-AI 공유 매체** — AppleScript가 살아남은 이유. 자동화 스크립트는 사람도 읽어야 함. LLM 친화성이 아니라 *사람 친화성*이 본질.
2. **프로젝트 정체성** — "AI와 OS가 글이라는 자연어로 대화한다"는 *내러티브가* 마케팅적으로 강력. 기술이 동일해도 이야기는 필요.
3. **장기 옵션** — §9.7의 글-네이티브 커널 마이그레이션 경로를 살리려면 글이 OS 안에 있어야 함.

**유의:**
- 글 언어를 정당화할 때 위 3가지를 사용하고, "LLM 친화성"은 빼거나 약하게 언급
- 영문 자료에서는 글을 "AppleScript의 AI 시대 후계자" 같은 *친숙한 비유*로 포지셔닝

### 3.3 글 vs 와이어 프로토콜의 관계 명확화

**문제:**
- 외부 청중이 "GeulOS는 글 언어로 동작한다"고 오해할 가능성
- 실제로는 *와이어 프로토콜이 OS 표준*이고 글은 그 위의 *선택적 흐름 제어 레이어*
- 단발 호출의 90%는 글 없이 직접 와이어 프로토콜 (§5.5, §6.1)

**유의:**
- README와 설계 문서에서 "GeulOS의 표준 인터페이스 = 와이어 프로토콜, 글은 흐름 제어 선택지" 라는 *층위 구분*을 분명히
- 글이 약해져도 OS는 살고, 글이 강해지면 OS도 강해지는 *디커플드 구조*를 명시

### 3.4 글 언어 의존성 리스크 (M5 SPOF)

**상황:** M5(글 AI 드라이버) 진척이 글 언어의 G1~G4에 직렬 의존.

**문제:**
- 글 언어는 별도 프로젝트이고 현재도 미성숙 (`문제점.txt`에 잔존 버그 — ADR-004 본문)
- §9.6에 "단일 개인 의존" 리스크로 본인이 명시했지만 완화책이 약함

**유의:**
- G3(호스트 함수 ABI)를 *조기에* 동결하고, GeulOS 측에서 *모의 글 VM*으로 M5 선행 가능하게 할 것
- 만약 글 G 시리즈가 6개월 이상 지연되면 **Lua/JavaScript를 임시 백엔드로 채택**하는 *비상 계획* 미리 작성. 글은 정체성/장기 옵션으로 유지하되, MVP 일정 보호.

## 4. 경쟁 환경 분석

### 4.1 이름 충돌 — "AIOS" (Rutgers)

**문제:**
- 폴더명 `C:\AiOS\`가 Rutgers의 AIOS와 충돌
- Rutgers AIOS는 COLM 2025 채택 + 학회에서 광범위 인용 + GitHub 별 다수
- 검색 시 본인 프로젝트가 묻힐 위험

**유의:**
- 공식 명칭은 **GeulOS**로 일관 (README는 OK)
- 폴더명·내부 명칭에서도 `AiOS` 흔적을 정리 (예: `C:\AiOS\` → `C:\GeulOS\` 검토)
- 모든 외부 자료에서 "GeulOS (글OS)" 표기, "AI OS" 같은 일반 용어 피하기

### 4.2 MCP가 점심을 빼앗을 수 있음

**상황:**
- Anthropic의 Model Context Protocol(MCP)이 "AI ↔ 도구 통신 표준"으로 자리잡음
- iOS 26에 시스템 통합 진행 중 (2025.09 보도)
- 수많은 앱이 MCP 서버를 노출 시작

**문제:**
- MCP는 *OS 교체 없이* "구조화된 AI 인터페이스"를 제공
- 만약 "모든 앱이 MCP 서버를 갖는다"가 표준이 되면 GeulOS가 풀려는 문제의 80%가 OS 없이 해결됨

**유의:**
- **GeulOS의 와이어 프로토콜과 MCP의 양방향 변환기 작성을 진지하게 검토**
- MCP를 적이 아닌 *진입 경로*로 활용 → MCP 생태계 전체를 무료로 가져옴
- GeulOS만의 차별점: *OS 차원의 통일 객체 트리 + 무료 매크로/undo* — MCP는 앱별 파편화로 이걸 못 함. 이 차별점을 끝까지 부각.

### 4.3 빅테크의 동일 방향 진입

**상황:**
- Apple: App Intents + MCP 시스템 통합 (iOS 26 진행 중)
- Google: A2UI (Opal, Gemini Enterprise에 이미 출시)
- Microsoft: Copilot + UI Automation 강화

**문제:**
- 셋 다 *AI-네이티브 인터페이스*로 가고 있고 자원·기기 보급이 GeulOS의 1000배+
- 시장 점유 경쟁에서 정면 충돌 시 100% 패배

**유의:**
- 시장 점유로 이기려 하지 말 것
- 대신 *"AI-네이티브 OS 아키텍처의 정답을 가장 먼저, 가장 명확하게 보여준 참조 구현"* 자리를 노릴 것
- Apple/Google이 GeulOS 설계 문서를 인용하게 만드는 것이 솔로 개발자의 최대 승리

### 4.4 유사 프로젝트와의 차별점 명문화 필요

**경쟁/유사 프로젝트 목록:**
- AIOS (Rutgers) — LLM-as-kernel, 학회 채택
- NeuroShellOS — "Semantic GUI Element" 개념 동일
- OpenDAN — Personal AI OS
- A2UI (Google) — Agent-to-UI 프로토콜
- App Intents (Apple) — 매니페스트 기반 액션 (GeulOS 시나리오 D와 동일)

**유의:**
- README/영문 자료에 *비교 표* 1개 포함 (GeulOS vs AIOS vs MCP vs App Intents)
- GeulOS만의 셀링 포인트 명문화:
  1. 풀 OS 대체 (PID 1 점유) — 프레임워크가 아님
  2. 단일 라이터 이벤트 루프 → 무료 매크로/undo/리플레이
  3. 사용자 클릭 ≡ AI 호출 (동일 파이프라인) — 어디서도 본 적 없는 대칭성
  4. AI-agnostic, 로컬 LLM 1급 지원 (T2 토폴로지)

## 5. 시장 진입 / 채택 전략

### 5.1 단계별 전략 (이전 답변 요약)

**1단계 (M2까지):** 글로 먼저 알리기
- 영문 기술 블로그 1편 ("Why Computer Use is broken: an OS-level alternative")
- 영문 README
- M2 시점에 1분 데모 영상

**2단계 (M4~M7):** 타겟 커뮤니티 침투
- Ollama / r/LocalLLaMA — T2 토폴로지의 정확한 타겟
- Rust + OS 커뮤니티 (Redox, Asahi 등 옆자리)
- 학술 발표 (HotOS, PLOS 워크숍 — 단독 저자 + 짧은 포지션 페이퍼)

**3단계 (MVP 이후):** 기업 접촉
- Anthropic — Computer Use의 더 나은 버전 제안
- Ollama / 로컬 LLM 회사
- 국내: 네이버 클로바, 카카오, 업스테이지

### 5.2 절대 피해야 할 함정

- ❌ MVP 전 독점 제휴 (IP/방향성 잠식)
- ❌ "모두를 위한 OS" 포지셔닝 (개발자 워크스테이션에 집중)
- ❌ "11개월 후 MVP" 같은 큰 약속 (작은 마일스톤으로 끊기)
- ❌ 한국어 단일 문서로 글로벌 청중 시도

### 5.3 성공 시나리오 재정의

| 시나리오 | 가능성 | 가치 |
|---|---|---|
| Windows 대체 대중 OS | <1% | — (현실적으로 불가능) |
| AI-네이티브 OS 설계의 *레퍼런스 구현* | 20~30% | 매우 높음 (논문, 채용, 인용) |
| AI 파워유저용 *니치 도구* | 15~25% | 중간 |
| 인수 또는 본인 채용 (Anthropic 등) | 5~10% | 인생 바뀜 |
| 미완성 | 40~50% | 학습 자산은 남음 |

**유의:** "Windows 대체"를 목표로 두면 무조건 실패. "참조 구현 자리"를 목표로 두면 30% 확률로 큰 승리.

## 8. 본인이 인지하지 못한 강점 (잊지 말 것)

이 분석은 위험에 집중했지만, 본인 프로젝트의 *진짜 자산*을 잊지 말 것:

1. **설계 문서가 학회 수준** — 단순 사이드 프로젝트가 아니라 publishable한 작업물
2. **5대 원칙이 일관됨** — 후속 모든 결정이 원칙으로 정당화됨. 이건 시니어 아키텍트의 설계
3. **보안 모델이 LLM 시대에 정확함** — "권한 매니저는 AI에게 RPC 노출 안 함"은 *킬러 보안 불변식*
4. **단일 라이터 이벤트 루프의 부수 효과** — 무료 매크로/undo/리플레이. Apple도 MCP도 못 함
5. **사용자 클릭 ≡ AI 호출의 대칭성** — 다른 어디서도 본 적 없음. 이게 GeulOS의 영혼
6. **ADR/Plan 작성 문화** — 협업자 영입과 외부 검증 시 큰 자산
7. **M1.5 `geulosh` 검증 도구** — 데모-주도 개발의 모범. 이 결정 자체가 뛰어남
8. **글 언어 사이드 프로젝트** — 부담이자 자산. 잘 활용하면 정체성, 잘못 활용하면 SPOF
