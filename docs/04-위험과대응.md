# 위험과 대응

발생 가능한 위험을 미리 명명하고, **신호·대응·폴백**을 사전에 적어 둔다. 위험을 만났을 때 즉흥 대응하면 패닉 결정이 나오고, 그 결정은 6개월 뒤 후회로 돌아온다.

## 2. 위험별 상세 (치명 + 높은 가능성 우선)

### R-01: 컴파일러 자체호스팅 회귀

**무엇**: 글 컴파일러에 OS 모드 추가하다가 stage2 ≠ stage3 가 됨. 자체호스팅 깨짐.

**발생 신호**:
- `python3 build.py --install` 실패
- stage2/stage3 SHA256 불일치
- 기존 테스트 회귀

**1차 대응**:
1. 마지막 통과 커밋으로 즉시 되돌리기 (git revert, reset 아님)
2. 변경분을 한 번에 하나씩 다시 적용하며 어느 변경이 회귀를 만들었는지 이등분 탐색
3. 회귀 원인 변경에 회귀 테스트 추가

**폴백 (1차 실패 시)**:
- `bootstrap/src/*.c` (C 부트스트랩) 컴파일러로 게이트 우회
- C 부트스트랩이 빌드 가능 상태인지는 **페이즈 0 첫 주에 검증** 해 둘 것 (보험)

**예방**:
- 페이즈 0 첫 주: 부트스트랩 빌드 확인 + CI 회귀 게이트 셋업
- 컴파일러 변경을 작은 PR로 나누고 매번 고정점 확인

---

### R-02: 한글 식별자 ↔ 조사 형태소 충돌

**무엇**: `타이머인터럽트`, `페이지테이블엔트리` 같은 OS 합성어 식별자가 글 렉서에서 조사로 잘못 쪼개져 컴파일러 세그폴트.

**발생 신호**:
- 컴파일러가 식별자 처리 중 죽음
- `[변수 이름]` 형태 어디서 잘려서 잘못 파싱
- 글 v0.7.3 changelog에 명시된 known constraint

**1차 대응**:
- 식별자를 즉시 우회 (`타이머인터럽트` → `Timer_Int` 식 영문 임시)
- 페이즈 0의 1주차 작업 "렉서 문맥 인식 강화"가 충분치 않았다는 신호

**폴백**:
- 페이즈 진행 일시 정지, 글 본가(`C:\workspace\geul`)로 복귀해 렉서 보강
- 보강 후 한글 식별자 재도입

**예방**:
- 페이즈 0의 1주차에 충분한 시간 투자 (4~5일)
- OS 코드 작성 시작 전에 합성어 식별자 1000개 테스트 케이스로 검증

---

### R-03: 컴파일러 격리 보증 부족 ★ 가장 큰 위험

**무엇**: 결정 A(소프트웨어 격리)의 핵심 가정 — 글 컴파일러가 임의 메모리 접근을 막을 수 있다 — 가 검증 안 됨. 글 컴파일러는 C 류의 자유로운 포인터 산술을 허용하므로 격리 보증을 위해 컴파일러 자체에 새 검증 단계 추가 필요.

**발생 신호**:
- 페이즈 2 spike에서 "이 글 코드가 다른 SIP 메모리를 침범할 수 있는데 컴파일 통과"
- 글 코드의 캐스트/포인터 산술이 검증 불가
- 검증 알고리즘 자체 구현이 6개월 이상 걸릴 것으로 추정

**1차 대응**:
- 페이즈 2 spike 결과 보고서 작성
- 격리 보증을 위한 최소 컴파일러 변경 범위 추산

**폴백 (구조적)**:
- 결정 A 폴백 발동 → 페이지 테이블 격리로 전환
- 결정 C(단일 주소공간)도 함께 폴백 → SIP마다 분리 주소공간
- 결정 E(메시지=포인터)도 영향 → 메시지가 데이터 복사로 변경 (성능 저하 감수)
- 작품 정체성 약화. `docs/00-비전과원칙.md`의 "차별점" 1·3번이 흐려짐

**예방**:
- **페이즈 1 후반에 페이즈 2 spike 일부를 미리 진행**: 컴파일러가 막을 수 있는 위반 종류 카탈로그 작성
- 검증 가능한 부분집합 정의 (예: "안전 부분집합 글" — 캐스트 금지, 포인터 산술 제한)

**완전 폐기 기준**:
- R-03 발동 + 결정 C·E도 폴백 ⇒ §4 폐기 기준 1번 발동 → 프로젝트 재정의

### R-04: 인라인 어셈블리 도입 비용 폭발

**무엇**: 컴파일러에 인라인 asm을 추가하는데 파서·IR·코드젠 전 계층 변경이 필요해 예상보다 4배 시간 소요.

**발생 신호**:
- 페이즈 0의 2~3주차 작업이 5주 넘어감
- 어셈블리 블록 안 식별자 해석에서 충돌

**1차 대응**:
- 인라인 asm 대신 **명명 인트린식**으로 후퇴 — 컴파일러 내장 함수처럼 `포트출력바이트(포트, 값)` → `out` 명령 emit
- 필요한 명령 7개만 (`cli`/`sti`/`hlt`/`in_b`/`out_b`/`lgdt`/`lidt`)
- 시간 박스: 이 폴백도 2주 이상 걸리면 다시 검토

**폴백 (2차)**:
- raw byte emission만 — 글 코드에서 `[정수[]] 명령바이트 = {0x0F, 0x01, ...}` 같은 식으로 직접 명령 바이트 박기
- 추함을 감수하고 페이즈 0 통과

**예방**:
- 페이즈 0 spike의 1주차에 인라인 asm 방식 선택 후 1주 데모로 결정 (인라인 asm vs 인트린식 vs raw bytes)

---

### R-07/R-08: 인터럽트·페이지 테이블 실수

**무엇**: 인터럽트 게이트 디스크립터, 페이지 테이블 엔트리의 비트 필드를 잘못 설정. 트리플 폴트로 끝없는 재부팅.

**발생 신호**:
- QEMU 무한 재부팅 (`-no-reboot -no-shutdown` 없으면 모름)
- Bochs 로그에 "exception during exception handling"
- 명령이 한 줄도 실행 안 됨

**1차 대응**:
- QEMU 옵션 `-d int,cpu_reset -no-reboot -no-shutdown` 으로 실행 → 트랩 로그 확인
- Bochs로 명령 단위 추적 (느리지만 결정적)
- Intel SDM Vol. 3의 해당 장 다시 읽기 (페이지 4-1, 6-1 등)

**폴백**: 없음. 이 부분은 빠져나갈 길이 없고 정확히 풀어야 함. 시간 박스만 두기 (1주 막히면 1주 쉬고 다시 보기)

**예방**:
- 페이즈 1 시작 시 Bochs 셋업도 같이 (`05-테스트환경.md` 참조)
- 인터럽트 게이트 / PTE 구조체에 글 묶음(struct) 정확 정의 + 비트 필드 주석

---

### R-09: IPC 성능 미달

**무엇**: 단일 주소공간이므로 메시지=포인터로 사실상 무료여야 하는데 1만 회/초 미달.

**발생 신호**:
- 페이즈 3 벤치마크: 두 SIP 핑퐁이 초당 1만 회 미만

**1차 대응**:
- 프로파일링: 호출 경로 어디서 시간 소비?
- 흔한 원인: TLB flush 발생(전체 주소공간 공유라면 발생 안 해야 함), 능력 검증 오버헤드, 캐시 라인 false sharing

**폴백**:
- 결정 E 부분 폴백: 핫 경로에 비동기 큐 추가 (이중 메커니즘 허용)
- 1만 → 1천으로 통과 조건 완화

**예방**:
- 페이즈 3 spike에 마이크로 벤치마크 셋업

---

### R-11: 영속 체크포인트 비용 폭발

**무엇**: 30초 간격 자동 체크포인트가 100MB SIP에서 1초 이상 걸려 사용성 무너짐.

**발생 신호**:
- 페이즈 4 spike에서 측정

**1차 대응**:
- 점진적 체크포인트 (dirty page 추적, MMU의 dirty bit 활용)
- 디스크 비동기 쓰기

**폴백**:
- 결정 D 폴백 → 명시적 저장 모델
- 작품 차별점 일부 손실 — 그러나 결정 A·B 살아 있으면 정체성 유지 가능

### R-13: 컴파일러 포팅 시 API 불일치 ★ MVP 직전 가장 큰 위험

**무엇**: 페이즈 5에서 글 컴파일러를 글 OS 위에 올리려는데, 컴파일러가 의존하는 `fopen`/`fread`/`printf`/`malloc` 등이 글 OS에 없거나 시맨틱이 다름.

**발생 신호**:
- 컴파일러 빌드 실패, 또는 빌드는 되지만 실행 시 syscall not found

**1차 대응**:
- 컴파일러 측에 추상 I/O 인터페이스 도입 (`std/io.gl` 추상화 강화)
- 글 OS 측에 호환 시뮬레이션 레이어 (POSIX 흉내 아님 — 글 표준 라이브러리 시뮬레이션)

**폴백**:
- 컴파일러를 글 OS API에 맞게 부분 재작성 (1~2개월)

**예방** ★ 중요:
- **페이즈 4 후반부터 페이즈 5 spike를 병행 시작** — 컴파일러가 의존하는 외부 함수 목록 카탈로그 작성
- 페이즈 5 시작 전에 컴파일러 측 추상화 변경분 미리 PR

---

### R-14: 풀타임 번아웃

**무엇**: 라이프 워크급 헌신을 1~2년 유지하다 동기·집중력 고갈.

**발생 신호**:
- 2주 이상 진척 없음
- 새 작업 시작이 며칠 미뤄짐
- 페이즈 문서 안 봐도 다 안다는 자만 (실제로는 잊고 있음)

**1차 대응**:
- 페이즈 일정 멈춤 선언 (1~2주 휴식, 의식적)
- 페이즈 문서 처음부터 다시 읽기

**예방**:
- 휴식을 일정에 포함 (페이즈 사이 2주 휴식 디폴트)
- 매주 금요일 진행 일지 — 안 쓰면 휴식 신호
- 작은 시각적 진척을 의도적으로 유지 (페이즈 2 안의 마일스톤 같은)

### R-15: 작품성 vs 진척 균형 손실

**무엇**: "작품으로서 OS"를 목표로 했으나 일정 압박에 휘둘려 의미 없는 흉내 OS가 됨. 또는 반대로 작품성 추구가 과해서 18개월에 부팅도 못함.

**발생 신호**:
- "기존 OS도 이렇게 하니까" 가 3번 이상 등장 → 작품성 무너짐
- 한 페이즈가 예상의 2배 시간 → 진척 무너짐

**대응**:
- `docs/00-비전과원칙.md` 5절 "의사결정 우선순위" 재독
- 결정 기록(`03-로드맵.md` §4)에 명시적으로 기록 — "이번에는 진척을 위해 작품성을 양보함" 식으로

## 3. 폴백 지도 (한 그림으로)

```
결정 A (컴파일러 격리) 폴백
    ├─→ 결정 C (단일 주소공간) 자동 폴백
    │       └─→ 결정 E (메시지=포인터) 영향, 데이터 복사 도입
    └─→ 차별점 1·3번 손실
        └─→ 폐기 기준 1번 발동 검토

결정 B (능력 보안) 폴백 (마지막 폴백)
    └─→ ACL 후퇴
        └─→ 차별점 2번 손실, 정체성 흔들림

결정 D (영속 메모리) 폴백
    └─→ 명시적 저장 모델
        └─→ 차별점 4번 손실, 작품성 유지 가능

결정 E (동기 메시지) 부분 폴백
    └─→ 큐 기반 비동기 추가 (이중 메커니즘 허용)
        └─→ 차별점 미손실
```

**결정의 무게**: A > B > C ≈ E > D. 위쪽일수록 폴백이 정체성에 큰 영향.

## 4. 폐기 기준 재확인

`03-로드맵.md` §7에서 정의한 폐기 기준. 둘 이상 동시 발생 시:

1. 결정 A 폴백 + 결정 C 폴백 → 차별점 거의 사라짐
2. 렉서 식별자 문제가 페이즈 1 이후에도 반복
3. 18개월 진행 후 페이즈 2 통과 못함
4. 풀타임 가용성 6개월 이상 끊김

이 표를 매 페이즈 회고 시 점검한다.
