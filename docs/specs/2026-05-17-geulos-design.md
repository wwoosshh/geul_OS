## 0. 한 줄 요약

> *AI에게 점자 설명서를 주는 OS.* 사용자에게는 GUI, AI에게는 CLI. 모든 상호작용 요소는 1급 객체이고 모든 동작은 이벤트이며, 글 언어는 AI ↔ OS의 자연어 글루로 동작한다.

## 1. 비전과 문제 정의

### 1.1 해결하고자 하는 문제

현재의 AI 자동화(OpenClaw·Computer Use 류)는 AI를 *고려하지 않은 시대의 환경* 위에서 사람의 행동을 모방하기 위해 막대한 자원을 낭비한다. AI는 "로그인 버튼을 누른다"는 의미를 이미 알지만, 그 의도를 픽셀 좌표로 변환했다가 다시 의미로 복원하는 왕복을 매번 반복한다. 그 왕복이 시간·토큰·오류율의 주범이다.

근본 원인은 OS와 앱이 *AI 관점에서 구조화되지 않았기 때문*이다. UI 요소는 픽셀로만 존재하고, 클릭은 사용자 동작으로만 정의되어 있으며, 매크로화·스크립트화가 사실상 불가능하다.

### 1.2 GeulOS의 가설

만약 OS가 처음부터 **AI를 1급 사용자**로 가정하고 설계된다면:

- 화면의 모든 상호작용 요소는 좌표가 아닌 **객체 ID**로 식별 가능
- 사용자의 클릭과 AI의 호출은 **같은 이벤트 파이프라인**을 통과
- AI는 스크린샷·좌표 계산 없이도 시스템 상태를 *정확히* 알 수 있음
- 어떤 신생 앱이라도 매니페스트만 선언하면 *자동으로* AI 접근 가능

### 1.3 핵심 비유

이 문서 전반에 걸쳐 두 비유를 시금석으로 삼는다.

> *"기존 AI 자동화는 시각장애인에게 옆에서 말로 설명해주는 것과 같다. GeulOS는 점자로 된 정식 설명서를 손에 쥐어주는 것이다."*

> *"OpenClaw는 눈을 감고 길거리 싸움을 하는 격이다. GeulOS는 눈은 감았지만 WWE처럼 대본이 정해진 무대다. AI는 미리 정해진 대로, 지금 느껴지는 그대로 동작하면 된다."*

모든 아키텍처 결정은 다음 시금석을 통과해야 한다:

> *이 결정이 AI에게 정해진 대본을 더 명확하게 만드는가, 아니면 더 추측에 의존하게 만드는가?*

## 2. 범위와 형태

### 2.1 GeulOS는 진짜 OS다

다만 Windows를 1:1로 대체하는 베어메탈 OS로 시작하지 않는다. 베어메탈은 드라이버 지옥(GPU·Wi-Fi·블루투스·프린터) 때문에 새 OS 99%가 실패하는 지점이다. GeulOS는 **하이퍼바이저 위의 게스트 OS**로 시작한다.

- 하이퍼바이저: QEMU / Hyper-V / VirtualBox 어디서든
- 게스트 인터페이스: **virtio** 한 세트만 지원
- 부팅 단위: 단일 디스크 이미지 (`geulos.img`)

**진짜 OS인 근거:** PID 1을 GeulOS의 객체 서버가 점유한다. POSIX 셸·X·Wayland·GNOME 같은 전통 사용자 공간이 일체 올라오지 않는다. 사용자 입장에서 부팅 후 보는 환경은 100% GeulOS다. (선례: macOS = Darwin 커널 + macOS 유저랜드, ChromeOS = Linux 커널 + Chrome 환경.)

### 2.2 사용자 / 사용 사례

장기적으로 AI를 OS 단에서 활용하는 모든 시나리오가 대상이다 — 개발·업무·자동화·연구. 그러나 **MVP는 개발자 워크스테이션(A 시나리오)** 부터 시작한다.

근거: 사용자 본인이 가장 잘 도그푸딩 가능, 글 언어와의 결합이 자연스러움, M4 이후 GeulOS 자체 개발에 AI를 끌어들이는 부트스트랩 루프가 가능.

## 3. 설계 원칙 (5)

이 5개는 후속 모든 결정의 시금석이다.

1. **모든 상호작용 요소는 1급 객체** — 픽셀로만 존재하는 UI는 없다.
2. **모든 동작은 이벤트** — 사용자 클릭 ≡ AI RPC ≡ 글 스크립트 메서드 호출. 셋이 동일한 파이프라인.
3. **사용자 뷰와 AI 뷰는 같은 객체의 두 투영** — 객체 트리는 하나, 렌더러는 둘. 항상 동기화.
4. **메모리·동시성 안전은 컴파일러가 강제** — Rust로 OS 코어. 안전을 코드 리뷰가 아니라 컴파일러가 차단.
5. **AI는 GeulOS에 *결합되지 않는다*** — OS는 LLM을 *번들/내장하지 않는다*. 다만 AI 서버가 *어디서* 도는지(클라우드, 호스트, VM 내부, 다른 머신)는 사용자 선택이며, GeulOS는 와이어 프로토콜로 *모든 배치 토폴로지*를 지원한다. (4.2 절 참고)

## 4. 아키텍처: 4층 모델

```
─── 외부 ──────────────────────────────────────────────
   AI 클라이언트 (Claude / GPT / 로컬 LLM)
                      │  TCP 또는 Unix 소켓
─── GeulOS 게스트 VM 안 ───────────────────────────
   ┌──────────────────▼──────────────────┐
   │ ① 글 AI I/O 드라이버 (Rust + 글 VM) │
   └──────────────────┬──────────────────┘
                      │  Rust trait
   ┌──────────────────▼──────────────────┐
   │ ② GeulOS 코어 (Rust)                │
   │   객체 서버 · 이벤트 버스           │
   │   컴포지터 · 권한 매니저 · 앱 런타임 │
   └──────────────────┬──────────────────┘
                      │  syscall
   ┌──────────────────▼──────────────────┐
   │ ③ Linux 커널 (C, 보이지 않음)       │
   │   드라이버 · FS · 네트워크          │
   │   PID 1 = ② 코어                    │
   └──────────────────┬──────────────────┘
                      │  virtio
─── VM 외부 ──────────────────────────────────────────
   ④ 하이퍼바이저
```

| 층 | 구현 언어 | 단 한 가지 책임 |
|---|---|---|
| ① 글 AI I/O 드라이버 | Rust(껍데기) + 글(VM 임베드) | AI의 자연어/스크립트를 OS 동작으로 번역 |
| ② GeulOS 코어 | Rust | 객체 트리와 이벤트 디스패치를 무결하게 유지 |
| ③ Linux 커널 | C (기존) | 하드웨어/리소스 추상화 |
| ④ 하이퍼바이저 | (외부) | VM 호스팅 |

### 4.1 글 언어의 위치

글 언어는 OS 뼈대 구현에 *쓰지 않는다*. 아직 미성숙하며, 새 OS의 안정성 약속을 처음부터 깨는 일이다. 대신 글이 진짜 강점을 가지는 자리 — **AI ↔ OS 자연어 글루** — 에만 배치한다. 글 코드는 AI 클라이언트가 보내고, 글 AI I/O 드라이버 안의 임베드 VM이 실행한다.

### 4.2 AI 배치 토폴로지 (Deployment Topology)

GeulOS는 AI 모델을 *번들·내장하지 않지만*, AI 서버가 어디에서 동작하든 모두 지원한다. 와이어 프로토콜이 Unix 도메인 소켓과 TCP 양쪽에 노출되기 때문이다.

**T1. 클라우드 API**

```
Claude/GPT API ◀── HTTPS ── AI 어댑터 (호스트) ── TCP ── GeulOS VM
```

호스트에 작은 어댑터 프로세스가 떠서, 클라우드 LLM의 응답을 GeulOS 프로토콜로 변환. 가장 강력한 모델 활용 가능, 호스트 인터넷 필요.

**T2. 호스트의 로컬 LLM 서버 (예: Ollama, LM Studio, llama.cpp)**

```
Ollama (호스트 :11434) ── HTTP ── AI 어댑터 (호스트) ── TCP ── GeulOS VM
```

사용자가 윈도우/맥 호스트에서 평소처럼 로컬 LLM 서버를 켜 둠. AI 어댑터가 Ollama의 응답을 GeulOS 프로토콜로 번역. *오프라인, 무료, 프라이버시 우위*. **본 사용자가 명시적으로 요청한 핵심 토폴로지.**

**T3. VM 내부의 로컬 LLM 서버**

```
Ollama (GeulOS VM 내) ── Unix sock ── GeulOS 코어
```

GPU 패스스루가 가능하거나 작은 모델을 쓸 때. VM이 자기 안에 모든 것을 격리.

**T4. 브라우저 기반 오케스트레이션 UI**

```
사용자 브라우저 (호스트) ──┬── Ollama (호스트)
                         └── GeulOS VM (TCP)
```

Open-WebUI 같은 웹 도구가 *두 서버 모두에* 동시 접속하여 사람-AI-OS 삼자 협업을 매개. 브라우저 자체가 *최상위 컨트롤러*가 됨.

**핵심:** 네 토폴로지 모두에서 GeulOS 측은 *동일*. AI 어댑터 / 오케스트레이션 UI는 GeulOS 외부에서 사용자 자유로 구성. GeulOS의 책임은 *프로토콜을 정확히 노출하는 것까지*.

## 5. 핵심 컴포넌트

```
        ┌────────────────────────────────────┐
        │  ⑦ 권한 · 정책 / 세션 매니저       │
        └────────────────────────────────────┘
                        ▲ 인가 질의
   AI 클라이언트        │   앱 프로세스        사용자 (창)
        │               │      │                  │
        ▼ ai.sock              ▼ app.sock          ▼
   ┌─────────────┐         ┌─────────────┐    ┌──────────────┐
   │ ⑤ 글 AI I/O│         │ ⑥ 앱 런타임 │    │ ④ 컴포지터  │
   │  드라이버  │         │             │    │              │
   └──────┬─────┘         └──────┬──────┘    └──────┬───────┘
          └───────┐  ┌───────────┘                   │
                  ▼  ▼                               │
           ┌──────────────────────────────────────┐  │
           │  ② 이벤트 버스 (단일 라이터)         │◀─┘
           └────────────────────┬─────────────────┘
                                ▼
           ┌──────────────────────────────────────┐
           │  ① 객체 서버 (단일 진실원)           │
           └──────────────────────────────────────┘
```

### 5.1 객체 서버 (① Object Server)

**책임:** 모든 의미 객체를 보관하고, 누가 무엇을 어떻게 바꿀 수 있는지의 유일한 권위.

```rust
struct Object {
    id: ObjectId,
    type_uri: TypeUri,       // 예: "aios.std/Button@1"
    parent: Option<ObjectId>,
    children: Vec<ObjectId>,
    props: Map<Key, Value>,
    state: Map<Key, Value>,
    methods: Vec<MethodSig>,
    owner: ActorId,
    acl: Vec<AclEntry>,
}
```

- 트리는 **앱 단위 서브트리의 숲(forest)**
- 객체 변경은 *반드시* 이벤트 버스 경유 (직접 mutate 금지)
- 객체 타입은 **버전 박힌 URI**(`aios.std/Button@1`)

### 5.2 이벤트 버스 (② Event Bus)

**책임:** 모든 이벤트에 *전순서*를 부여하고 구독자에게 같은 순서로 전달.

```rust
struct Event {
    id: EventId,            // 단조 증가
    actor: ActorId,
    target: ObjectId,
    kind: EventKind,        // Invoke, StateSet, Lifecycle, ...
    payload: Value,
    causation: Option<EventId>,
}
```

**단일 라이터 모델.** 한 스레드가 이벤트 큐를 직렬로 처리. 락 없음, 데이터 레이스 없음. 부수 효과로 **이벤트 로그 = 시스템 전체 매크로/녹화/리플레이**, **undo/redo가 OS 1급 기능**, **AI에게 정확한 인과 보고** 모두 무료.

### 5.3 와이어 프로토콜 (③ Wire Protocol)

**책임:** 외부에서 객체 서버와 대화하는 유일한 메시지 포맷.

| 클라이언트 | 엔드포인트 | 역할 |
|---|---|---|
| AI (VM 내부) | `/run/aios/ai.sock` (Unix) | RPC + 글 스크립트 |
| AI (VM 외부) | `:<port>` (TCP, mTLS 또는 토큰) | 동일. T1·T2·T4 토폴로지를 위함 |
| 앱 | `/run/aios/app.sock` (Unix) | 자기 객체 게시·조작 |
| 컴포지터 | (커널 내부 IPC) | 트리 구독·렌더링 |

AI 엔드포인트는 Unix 소켓과 TCP 양쪽에 *동일 프로토콜*로 노출된다. TCP는 mTLS 또는 발급된 토큰으로 인증한다. VM 외부의 어댑터·UI가 자유롭게 접속.

| 메시지 | 방향 | 의미 |
|---|---|---|
| `Hello` | 클라 → 서버 | 핸드셰이크, 역할·인증 |
| `Mount` | 앱 → 서버 | 자기 서브트리 게시 |
| `Invoke` | 클라 → 서버 | 객체.메서드(인자) 호출 |
| `Subscribe` | 클라 → 서버 | 변화 구독 |
| `Event` | 서버 → 클라 | 발생 통보 |
| `Query` | 클라 → 서버 | 트리 조회 |
| `Glscript` | AI → 서버 | 글 코드 실행 |

**프로토콜은 앱과 AI에게 동일.** "AI에게 보이는 것 ≡ 앱이 의도한 것"을 자동 보장.

### 5.4 컴포지터 (④ Compositor)

**책임:** 객체 트리를 *읽어* 사람의 모니터에 그린다. *쓰지 않는다.*

- 객체 서버를 `Subscribe`로 구독
- 입력(키보드/마우스) → 이벤트로 변환 → 이벤트 버스 enqueue (직접 mutate 금지)
- 렌더링: wgpu 기반 자체 렌더링 (virtio-gpu 활용)

### 5.5 글 AI I/O 드라이버 (⑤)

**책임:** AI의 `Invoke`(단발)와 `Glscript`(다단계)를 받아 객체 서버에 안전하게 전달.

- **단발 RPC는 글을 거치지 않음.** 마이크로초 단위 직통.
- **글 스크립트는 임베드 VM에서 실행.** 매번 AOT 컴파일하지 않음 — 인터프리터/바이트코드 VM 필수.
- **호스트 함수 디스패치 테이블** 외의 OS API 접근 금지 (모래상자).
- 실행 예산(opcode/메모리/시간) 강제.

### 5.6 앱 런타임 (⑥)

**책임:** 앱을 *별 OS 프로세스*로 실행하고 권한을 등록.

- 앱 = 별 프로세스 (충돌 격리)
- `app.sock` 연결 → `Hello` + 매니페스트 → 권한 동의 → `Mount`
- MVP에서는 글 컴파일러로 만든 ELF만. 후속에 컨테이너로 레거시 호환.

### 5.7 권한 · 세션 매니저 (⑦)

**책임:** 모든 호출에 대해 *호출자 ↔ 객체 ↔ 액션* 삼각형 검사.

- Capability + 사용자 Consent 모델
- 앱: 매니페스트의 카테고리 권한, 설치 시 1회 동의
- AI 세션: 범위 좁은 토큰, 만료 가능, 권한 회수 가능

### 5.8 컴포넌트 의존성 (단방향)

```
권한매니저 ◀── 모두 (인가 질의)
객체 서버 ◀── 컴포지터, 앱런타임, 글AI드라이버
이벤트버스 ◀── 객체 서버 ◀── 모두
```

순환 없음. 각 컴포넌트는 자기보다 깊은 층만 호출.

## 6. 데이터 흐름 — 5개 시나리오

### 6.1 시나리오 A — AI 단발 RPC

> *"메모장의 저장 버튼을 눌러줘"*

```
AI → 글 AI 드라이버 → 권한매니저(인가) → 이벤트 버스(직렬화)
   → 객체 서버 → 앱 프로세스 → 상태 갱신
   → 이벤트 버스 → 구독자들에게 통보 → AI에게 Ack(이벤트 ID)
```

- 글 인터프리터 *우회*. 단발은 직통.
- 레이턴시 예산: 100µs ~ 1ms (OpenClaw 대비 4~5 자릿수 개선)

### 6.2 시나리오 B — AI 다단계 글 스크립트

> *"열린 모든 메모장에서 '오늘'이 들어간 줄만 골라 새 파일로 모아줘"*

```
AI → Glscript 메시지 → 글 AI 드라이버
   → [안전 모드 검사 → 바이트코드 캐시 조회/컴파일]
   → 글 VM 실행 (호스트 함수들을 통해 RPC 호출 반복)
   → 종료 시 FinalResult(이벤트 ID 목록 + stdout) → AI
```

- 글이 OS와 대화하는 단위는 결국 *같은 RPC*. 글은 "여러 RPC를 묶는 흐름 제어".
- 바이트코드 캐싱으로 반복 호출 이득.
- AI는 *하나의 응답*만 받음 — *맥락 폭발* 없음.

### 6.3 시나리오 C — 사용자 클릭 (대칭성)

```
사용자 마우스 → 컴포지터 (좌표 → ObjectId 변환)
   → 이벤트 (actor: user) → 이벤트 버스
   → 이후 시나리오 A의 4번째 단계부터 동일
```

**이게 GeulOS의 영혼이다.** 사용자 클릭과 AI 호출이 이벤트 버스 이후 *완전히 같은 경로*. 모든 매크로·녹화·재생이 자동으로 작동.

### 6.4 시나리오 D — 앱이 자기 UI 게시

```
앱.exe → connect(app.sock) → Hello + 매니페스트
   → 권한 매니저 검증 → Ack
   → Mount(서브트리) → 객체 서버 인스톨 → MountAck
   (이 시점부터 사용자 GUI에 표시, AI 조회 가능)
```

**매니페스트가 곧 계약서.** 선언하지 않은 권한은 사용 불가. 표준 타입은 AI가 학습된 능력으로 즉시 다룸. 커스텀 타입은 매니페스트의 시그니처·의미 주석으로 *즉석 이해 가능* — **신생 앱(예: 가상의 pppt)도 매니페스트만 있으면 자동 AI 접근 가능**.

### 6.5 시나리오 E — AI Subscribe

```
AI → Subscribe(target, kinds) → 글 AI 드라이버 → 객체 서버(등록)
   ⋯ 시간 경과 ⋯
사용자 입력 → 상태 변경 이벤트 → 객체 서버 → 매칭 구독 → 글 AI 드라이버 → AI(통보)
```

AI는 폴링하지 않음. 토큰·시간·돈 모두 절약.

### 6.6 데이터 흐름 불변식 (F 시리즈)

| # | 불변식 |
|---|---|
| F1 | 모든 mutate는 이벤트 버스 경유 |
| F2 | 모든 `Invoke`는 권한 게이트 후 이벤트 큐 진입 |
| F3 | 컴포지터는 객체 서버에 쓰지 않음 |
| F4 | 글 코드는 호스트 함수 디스패치 테이블만 사용 |
| F5 | AI 호출과 사용자 입력은 동일 이벤트 형식·디스패치 경로 |

## 7. 오류 처리 / 보안 경계

### 7.1 신뢰 영역

```
[T0] 사용자 본인               ────── 궁극의 권위
[T1] 컴포지터·권한매니저·객체서버 ─── TCB (믿어야만 함)
[T2] 앱 런타임·글 AI 드라이버  ────── 중간 신뢰
[T3] 사용자 앱                ────── 낮은 신뢰
[T4] AI 클라이언트            ────── 기본 *불신*
[T5] 글 스크립트              ────── 모래상자
```

**AI는 기본 불신.** "AI는 도구이지 주인이 아니다." 사용자 명시 동의 없이 권한 자동 상승 없음.

### 7.2 위협 모델

| # | 위협 | 어디서 막나 |
|---|---|---|
| TH-1 | AI 권한 없는 객체 접근 | 권한 매니저 게이트 |
| TH-2 | 글 스크립트 무한 루프·메모리 폭증 | VM 예산 |
| TH-3 | 악성 앱이 타 앱 객체 조작 | 객체 ACL: 소유자만 mutate |
| TH-4 | 앱이 AI 소켓 도청 | 별 소켓·별 인가 |
| TH-5 | 프롬프트 인젝션 | 컨텐츠와 명령 분리해 전달 |
| TH-6 | AI 토큰 유출 | 단명·범위제한·디바이스 외 발급 X |
| TH-7 | 코어 크래시 | Rust 안전성 + `unsafe` 감사 + 프로세스 분리 |
| TH-8 | 컴포지터 표시 속임 | 권한 다이얼로그 시 사용자 알림 |

**범위 밖:** 하이퍼바이저 자체 취약점, 호스트(Windows) 측 키로거, 양자컴퓨터.

### 7.3 오류 분류

| 분류 | 처리 |
|---|---|
| E-Input | 호출만 거부 |
| E-Policy | 거부 + 감사 로그 |
| E-App | 앱 서브트리 비활성 마킹, 다른 앱 무영향 |
| E-Resource | 글 VM 강제 종료, 부분 효과는 로그에 남아 되돌리기 가능 |
| E-Internal | 객체 서버 패닉 → 이벤트 로그 덤프 → 재시작 → 로그에서 트리 복원 |
| E-Fatal | 커널 죽음, 재부팅 후 로그에서 복원 |

이벤트 로그가 *원천 진실*, 객체 트리는 *유도 상태* (Event Sourcing).

### 7.4 격리

| 컴포넌트 | 프로세스 | 죽으면 |
|---|---|---|
| 객체 서버 + 이벤트 버스 + 권한 매니저 | PID 1 (단일) | 재부팅, Rust 안전성으로 거의 방어 |
| 컴포지터 | 별 프로세스 | AI는 계속 동작 가능, 컴포지터만 재기동 |
| 글 AI 드라이버 | 별 프로세스 | AI 연결만 끊김, 사용자 GUI 무사 |
| 각 앱 | 별 프로세스 | 격리 |

### 7.5 권한 모델

```
권한 = (ObjectId 또는 Pattern, MethodName 또는 *, 만료시각, 사용횟수한도)
```

- **앱:** 매니페스트 카테고리 권한, 설치 시 1회 동의
- **AI 세션:** 좁은 범위·만료·재발급 가능 토큰
- **동의 다이얼로그:** 1회 / 이 세션 / 영구
- **회수:** 언제든 토큰 폐기

### 7.6 감사 / 이벤트 로그

이벤트 로그는 *전순서 + 영속*이므로 다음이 무료:

- **누가/언제/무엇을** 결정적 추적
- **AI의 의도하지 않은 동작** 사후 검증
- **사용자 "되돌리기"** = 로그 역재생, OS 1급 undo

**기본값: 마지막 N개만 영속, 사용자 설정 가능.** AI 글 스크립트 원문 저장 여부는 별 설정.

### 7.7 AI-특화 우려

| 우려 | 처리 |
|---|---|
| 프롬프트 인젝션 | 응답에서 *컨텐츠와 명령 다른 필드*로 분리 |
| 호출 폭증 비용 | 토큰별 분당 한도 |
| 민감 데이터 누출 | `aios.secret/*` 타입은 AI 세션 그래프에 사용자 명시 허용 없이 등장 안 함 |
| 권한 상승 | 권한 매니저는 AI에게 RPC 노출 안 함, 변경은 사용자 GUI/설정 파일로만 |

### 7.8 보안 불변식 (S 시리즈)

| # | 불변식 |
|---|---|
| S1 | AI 토큰은 발급 시 권한 범위 박힘, 범위 밖 호출 거부 |
| S2 | 권한 매니저는 AI 클라이언트에 RPC 노출 안 함 |
| S3 | 객체는 소유자 외 mutate 불가 (서버 강제) |
| S4 | 모든 이벤트는 액터 기록, 사후 감사 가능 |
| S5 | 글 스크립트는 opcode·메모리·시간 예산 보유 |
| S6 | `aios.secret/*` 는 사용자 명시 허용 없이 AI 그래프에 등장 안 함 |

## 8. 테스트 전략

### 8.1 테스트 레이어

| 레이어 | 내용 | 비고 |
|---|---|---|
| L0 | 단위 테스트 (Rust `#[test]`) | CI 1분 미만 |
| L1 | 속성 기반 (proptest) | **평균 이상 투자** |
| L2 | 컴포넌트 단위 | mock 사용 |
| L3 | 프로토콜 적합성 | 소켓 실제 송수신 |
| L4 | E2E 통합 | QEMU 부팅 |
| L5 | AI 시나리오 | **GeulOS만의 특별한 층** |

### 8.2 핵심 속성 (L1)

| 속성 | 검증 |
|---|---|
| P1 | 임의 mutate 순열 후 트리 무결성 |
| P2 | 같은 이벤트 로그 재생 → 같은 트리 (결정론) |
| P3 | 액터 A는 액터 B 소유 객체 mutate 불가 |
| P4 | 어떤 글 스크립트도 예산 내 종료 |
| P5 | 메시지 직렬화 → 역직렬화 라운드트립 |

### 8.3 L5: AI 시나리오 테스트

실제 LLM에 자연어 작업을 주고 GeulOS 프로토콜로 완수하는지 측정.

- 지표: 성공률, 호출 수, 토큰 사용량, 평균 latency
- 매 PR이 아니라 일정 주기 (매일/주별)
- 회귀: 성공률 하락 시 알림
- 시나리오 예: 메모장 작성, 가공의 신생 앱(pppt 비유) 매니페스트 보고 작업

### 8.4 결정론 보장 도구

- 결정론적 시계 (테스트 모드)
- 결정론적 ID 발급기
- 이벤트 로그 → 트리 재생기 (P2를 모든 통합 테스트가 덤으로 검증)
- 시드 가능 PRNG

### 8.5 정적 분석

`clippy` / `cargo audit` / `cargo deny` / `miri` / `cargo fuzz` / `unsafe` 인덱스(매 PR 신규 unsafe 별도 리뷰).

### 8.6 CI 게이트

L0 + L2 + clippy + L1(N분 한도) + L3 + 스펙-구현 일치. L4·L5는 게이트가 아닌 *추세 모니터링*.

### 8.7 첫 90일 최소치

L0(단위), L1(P1·P5), L3(메시지 종류별 1개), L4(단일 e2e). L5와 P2~P4는 컴포넌트 안정 후.

## 9. MVP 범위와 마일스톤

### 9.1 MVP 정의

> *"QEMU에서 부팅된 GeulOS에서, 외부 Claude API가 GeulOS 위의 글-네이티브 메모장을 자연어로 조작해 텍스트를 작성·저장·재열어볼 수 있다."*

이 한 문장이 만족되면 4층 아키텍처 전체가 살아있음이 증명됨.

### 9.2 마일스톤 (M 시리즈)

| ID | 목표 | 기간 |
|---|---|---|
| **M0** | 부트스트랩 (스펙·CI·구조·ADR) | 4주 |
| **M1** | 객체 서버 + 이벤트 버스 (인-메모리) | 8주 |
| **M2** | 와이어 프로토콜 (Unix 소켓) | 4주 |
| **M3** | 앱 런타임 + 권한 매니저 | 4주 |
| **M4** | 컴포지터 (사용자 GUI) | 8주 |
| **M5** | 글 AI I/O 드라이버 (G 의존) | 8주 |
| **M6** | VM 부팅 통합 (PID 1) + AI 엔드포인트 TCP 노출 | 4주 |
| **M7** | 도그푸딩 (메모장 + AI 시나리오) | 4주+ |

각 마일스톤은 **검증 가능한 단일 데모**로 끝남.

### 9.3 글 측 마일스톤 (G 시리즈, 병렬)

| ID | 작업 | 기간 |
|---|---|---|
| **G1** | AST → 바이트코드 변환기 | 4주 |
| **G2** | 바이트코드 VM (Rust 임베드) | 6주 |
| **G3** | 호스트 함수 디스패치 ABI 명세 | 2주 |
| **G4** | 안전 모드 의미 검사기 | 3주 |

**문법 재설계 없음.** 파서·AST 공유, 백엔드만 추가. 사용자 코드 변경 없음.

### 9.4 누적 일정

| 단계 | 누적 |
|---|---|
| M0 | 1개월 |
| M1 | 3개월 |
| M2 | 4개월 |
| M3 | 5개월 |
| M4 | 7개월 |
| M5 | 9개월 |
| M6 | 10개월 |
| **M7 / MVP** | **11개월** |

풀타임 단독 개발자 + AI 보조 기준의 낙관적 추정. 파트타임이면 1.5~2배.

### 9.5 명시적 MVP 제외 사항

- 베어메탈 부팅 / 멀티 사용자 / 다중 모니터
- 레거시 Linux 앱 컨테이너 / Wayland·X 호환 / GPU 셰이더 API
- 시간 여행 디버거 UI / 네트워크 앱(브라우저)
- 한글 IME (기본 키보드만)
- AOT 글 JIT (바이트코드 VM만)

### 9.6 주요 리스크와 완화

| 리스크 | 완화 |
|---|---|
| 글 바이트코드 VM 단일 개인 의존 | G3 ABI 조기 동결 → GeulOS 측이 모의 글 VM으로 M5 선행 |
| Rust async + wgpu 학습 곡선 | M4 직전 1주 학습 스파이크 |
| AI 시나리오 비결정성 | N회 실행 통계 추세 |
| Linux 의존이 객체 모델 순도 흐림 | syscall을 얇은 레이어로 격리, 후속 글-네이티브 커널 마이그레이션 경로 명시 |

### 9.7 재결정 시점

- **M2 완료:** 와이어 프로토콜 v0.1 → v1.0 동결 여부
- **M4 완료:** wgpu 채택 재검토
- **M7 완료:** Linux 유지 vs 글-네이티브 커널 마이그레이션 — 첫 큰 갈림길

각 시점에서 ADR 추가, 결정 근거 영구 기록.

## 10. 부록

### 10.1 핵심 의사 결정 요약 (ADR 시드)

| ADR | 결정 | 근거 |
|---|---|---|
| ADR-001 | Linux 커널 채용, GeulOS는 PID 1 점유 | 드라이버 생태계 무료, 진짜 OS 자격 유지 |
| ADR-002 | OS 뼈대는 Rust | 메모리 안전 컴파일러 강제, 빅3 OS도 Rust로 이주 중 |
| ADR-003 | 단일 라이터 이벤트 루프 | 락 없음, 결정론, 이벤트 로그 = 매크로·undo 무료 |
| ADR-004 | 글 언어는 AI ↔ OS 글루 (뼈대 X) | 글은 미성숙, OS 안정성 약속 보호 |
| ADR-005 | AI는 GeulOS에 결합되지 않음, 모든 배치 토폴로지 지원 (Unix + TCP 노출) | AI-agnostic, 모델 교체 자유, 로컬 LLM 서버(Ollama 등) 우대, OS 범위 축소 |
| ADR-006 | 매니페스트 기반 권한 | 신생 앱 자동 AI 접근, 명시적 계약서 |
| ADR-007 | Rust async + wgpu 컴포지터 | virtio-gpu 자연스러움, Rust 생태계 표준 |
| ADR-008 | 글 바이트코드 VM (인터프리터 모드) | 매 호출 AOT 컴파일은 latency 폭증 |
| ADR-009 | AI 기본 불신 + Capability + Consent | "AI는 도구이지 주인이 아님" |

### 10.2 용어

- **객체 (Object):** 시스템 안의 상호작용 가능한 단위. 고유 ID, 타입 URI, 부모, 자식, props, state, methods, owner, ACL을 가짐.
- **타입 URI:** `aios.std/Button@1` 형식의 버전이 박힌 객체 타입 식별자.
- **이벤트 (Event):** 객체 상태 변경을 일으키거나 통보하는 단위. 단조 EventId, actor, target, kind, payload, causation.
- **액터 (Actor):** 동작을 일으킨 주체. 사용자 / AI 세션 / 앱.
- **매니페스트:** 앱이 시작 시 게시하는 자기 정체·권한 요구·UI 타입 목록.
- **호스트 함수:** 글 VM 안에서 호출 가능한, GeulOS 측 Rust 함수. 디스패치 테이블로 노출됨.
- **TCB (Trusted Computing Base):** 객체 서버 + 이벤트 버스 + 권한 매니저. 이 셋이 깨지면 모든 약속이 깨짐.
