# 페이즈 2 — 메모리와 격리 (★ 핵심 검증)

**기간**: 약 4~6개월 (15~20주)
**핵심 작업**: 메모리 관리 + **소프트웨어 격리(결정 A) 검증** + 첫 SIP 실행
**다른 페이즈와의 관계**: 이 페이즈가 글 OS의 정체성을 결정한다. spike 결과에 따라 결정 A·C·E가 폴백할 수 있음.

## 통과 조건

1. **물리 페이지 할당기 동작**: 4KB 페이지 할당/해제, 누수 없음
2. **가상 페이지 매퍼 동작**: 임의 물리→가상 매핑, 4KB와 2MB 페이지 모두
3. **힙 동작**: `메모리할당(n)` / `메모리해제(p)` 사용 가능
4. **첫 SIP 실행**: framekernel이 글로 작성된 "헬로 SIP"를 로드해 실행
5. **격리 시연 (★ 정체성)**: 다음 중 한 가지가 동작
   - 5a. **글 컴파일러가 SIP의 잘못된 메모리 접근을 컴파일 타임에 거부** (안전 부분집합 적용 시)
   - 5b. **런타임에 정의된 트랩으로 잡힘** (페이지 테이블 격리 폴백 시)
6. **두 SIP가 동시 메모리 격리**: SIP A의 메모리 영역을 SIP B가 침범 불가

## spike (★ 2~4주 시간박스, 가장 큰 검증)

**핵심 질문**: 결정 A(소프트웨어 격리)가 글 컴파일러로 보증 가능한가?

### spike-1: 위반 종류 카탈로그 (1주)

글 코드에서 일어날 수 있는 메모리 안전성 위반을 모두 열거:

1. 배열 경계 초과
2. NULL 포인터 역참조
3. 해제된 포인터 사용 (use-after-free)
4. 잘못된 캐스트 (int → 포인터)
5. 포인터 산술로 의도하지 않은 영역 도달
6. 인덱스가 음수
7. 구조체 필드 접근이 잘못된 타입에서

각 위반에 대해: 현재 글 컴파일러가 잡는가? 잡을 수 있는가? 잡기 위한 변경 규모?

### spike-2: 안전 부분집합 정의 (1주)

격리 보장 가능한 글 부분집합을 정의:
- 모든 배열 접근에 컴파일 타임 또는 런타임 경계 검사
- 포인터 캐스트 금지 (또는 매우 제한적 허용)
- 임의 포인터 산술 금지 — 배열 인덱싱만 허용
- 능력 토큰 외에는 다른 SIP 메모리에 대한 참조 보유 불가

### spike-3: 검증 컴파일러 변경 추산 (1주)

안전 부분집합을 강제하는 컴파일러 변경의 작업량 추산:
- 1주? 1개월? 6개월?
- 결과에 따라 진행 또는 폴백 결정

### spike 결과 → 페이즈 2의 노선 결정

- **결과 A**: 안전 부분집합 + 컴파일러 변경 2개월 이내 → 결정 A 살림. W3 본 작업 시작
- **결과 B**: 컴파일러 변경 6개월 이상 또는 보증 불가 → 결정 A 폴백. 페이지 테이블 격리로 전환. 결정 C도 자동 폴백 (분리 주소공간), 결정 E도 영향

**결과는 결정 기록(03-로드맵.md §4)에 한 줄**.

## 위험과 폴백

### R-03 (★): 컴파일러 격리 보증 부족
- spike 결과 B → 결정 A 폴백 즉시 발동
- **결정 기록 갱신 필수**
- 작품 정체성 손실 → `00-비전과원칙.md` 재독 + 의미 점검

### R-08: 페이지 테이블 매핑 실수
- 매우 흔함. 잘못된 PTE → 페이지 폴트
- **대응**: 페이지 테이블을 hex dump 가능한 디버그 함수 미리 작성

### 안전 부분집합이 너무 좁아 실용성 없음
- spike에서 발견 시: 부분집합 완화 + 검사 강화 시도
- 그래도 안 되면 결정 A 폴백

### SIP 메타데이터 형식이 ELF로 부족
- 확장 ELF 노트 섹션 활용
- 또는 SIP 자체에 매니페스트 함수 (`[SIP매니페스트]은 → 매니페스트 { ... }`) 정의
