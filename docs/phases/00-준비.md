## spike (1~2주 시간박스)

**핵심 질문**: 글 컴파일러에 인라인 어셈블리를 어떤 형태로 도입할 것인가?

### 후보 3가지

1. **인라인 asm 블록**: `어셈블리 { "cli"; "out 0x20, al"; }`
   - 장점: 가장 표현력 높음
   - 단점: 파서·IR 큰 변경, asm 안 식별자 해석 복잡

2. **명명 인트린식**: `포트출력바이트(0x20, 0x20)` → `out` 명령
   - 장점: 컴파일러 변경 작음, 안전
   - 단점: 새 명령 필요할 때마다 인트린식 추가

3. **원시 바이트 emit**: `[정수] 명령들 = {0x0F, 0x01, ...}` 가 코드 영역에 박힘
   - 장점: 컴파일러 변경 최소
   - 단점: 가독성 나쁨

### W2 spike — 2026-05-14 — R-02 lexer 합성어 분리 1차 시도

**확인된 사실**

### W2 spike 2회차 — 2026-05-15 — R-02 본격 추적

**자동 등록 카탈로그 캡쳐** (trace 추가 + 빌드 + 자체 컴파일):
- 7개 어근 식별: 거짓레이블, 레지스터, 모드, 소속이름, 정렬단위, 코드, 타입번호
- 모두 함수 매개변수 컨텍스트의 정상 분리 (`[X로 ...]`, `[X과 ...]`)

**시도 3: 컨텍스트 구분 (매개변수선언모드 flag)**:
- 새 flag로 매개변수만 분리, 일반 선언은 통째 등록
- 빌드 통과, 387,072 bytes
- **stage3 자체 컴파일 시 parser 무한 루프** (60+초 타임아웃)

**무한 루프 근본 원인 추적** (stage 1.7 진입 단어 trace):
- 트레이스 분석으로 **글 syntax 자체의 의존성 발견**:
  - `정수 읽은길이는 strlen(대상).` ← `는` 조사로 변수 초기화 (= 등가)
  - 이 syntax는 lexer가 `읽은길이는`을 `읽은길이` + `는`으로 **분리해야 성립**
  - 내 fix가 변수 선언에서 분리 차단 → parser가 `읽은길이는` 통째 식별자 받음 → 다음 토큰 `strlen` 위치에서 "타입이 필요합니다" 무한 오류
- 즉 `정수 X는 값.` syntax가 lexer의 조사 분리에 의존

**결정적 깨달음**
- **R-02는 글 언어 자체의 디자인 변경 규모**. lexer가 변수 이름을 합성어로 보존할지, 조사를 분리할지 결정하는 정보가 **현재 syntax에 없음**.
- `정수 블록와이 = 42.` (분리 X 의도) vs `정수 읽은길이는 strlen.` (분리 O 의도)을 lexer는 구분 불가.
- 해결책 후보:
  1. **새 syntax 도입**: `정수 X.` (자동 분리 X), `정수 X{는,을,...} 값.` (명시 분리 O) — 모든 글 코드 마이그레이션 필요
  2. **lexer/parser interface 재설계**: parser가 raw word 받고 *자체적으로* 분리/등록. lexer는 단순 토큰 emit
  3. **휴리스틱 강화**: 어근이 4음절+이면 분리 안 함 (긴 합성어는 변수 이름) — 부정확
- 어느 후보든 **페이즈 0 W2의 단일 1주차 작업 범위 초과**. 페이즈 0 후반의 별도 spike 또는 페이즈 1 진입 후 본격 작업.
