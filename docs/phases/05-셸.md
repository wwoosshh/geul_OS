# 페이즈 5 — 셸과 자체호스팅 (MVP 도달)

**기간**: 약 3~6개월 (12~20주)
**핵심 작업**: 글-셸 + 라인 에디터 + 글 컴파일러를 글 OS 위에 포팅
**다른 페이즈와의 관계**: 모든 이전 페이즈가 전제. 이 페이즈 통과 = **북극성 달성**.

이 문서는 페이즈 4 통과 후 다시 상세화한다. 지금은 윤곽 + 가장 큰 위험 R-13의 사전 대응.

## 통과 조건 = MVP

`docs/00-비전과원칙.md`의 북극성:

> 글 OS 안에서 글 컴파일러 소스를 편집·빌드해서 그 OS 자체를 다시 컴파일할 수 있다.

구체:

1. **글-셸 동작**: 글 문장을 입력하면 실행됨. `편집 hello.gl`, `빌드 hello.gl`, `실행 hello` 모두 동작
2. **라인 에디터 동작**: 한글 파일 편집·저장. ed 또는 vim 모드 일부
3. **컴파일러 실행**: 글 OS 위에서 `compiler` SIP 실행 가능
4. **자체호스팅 고정점 (★)**: 글 OS에서 글 컴파일러 소스 트리를 컴파일러로 빌드 → 결과 바이너리가 동일 소스를 다시 빌드 → stage2 == stage3
5. **글 OS 자체를 글 OS에서 빌드**: 글 OS 소스 (`C:\workspace\geul_operater\*`) 를 글 OS 안에서 빌드해서 새 ELF 생성

## spike (페이즈 4 후반부터 미리)

### spike-1 (★): 컴파일러 외부 의존 함수 카탈로그
- 현재 글 컴파일러가 의존하는 모든 외부 함수 목록화 (`fopen`, `fread`, `fwrite`, `fclose`, `printf`, `malloc`, `free`, `exit`, `strcmp`, `strlen`, ...)
- 각각이 글 OS의 어떤 시스템 콜에 매핑되는가
- 의미가 다른 부분 (예: `errno` 모델 vs 능력 모델) 식별

### spike-2: 컴파일러 추상 I/O 인터페이스
- 글 컴파일러 측에 추상 인터페이스 도입 (`std/io.gl` 강화)
- Windows 빌드는 PE+msvcrt, 글 OS 빌드는 글 OS API
- 같은 컴파일러 소스가 두 환경에서 컴파일 가능해야 함

## 본 작업 (윤곽)

### 글-셸
- 줄 단위 입력 → 글 문장으로 파싱
- `편집 X` → 에디터 SIP에 메시지
- `빌드 X` → 컴파일러 SIP에 메시지
- `실행 X` → 새 SIP 로드
- `목록`, `삭제`, `복사` 등 기본 명령

### 라인 에디터
- ed 스타일이 가장 단순 (라인 번호 + 명령). 작품성 ★
- 또는 vim-lite (페이즈 5 초과 가능성 큼)
- 한글 입력 — 페이즈 5의 입력기 작업 필요할 수도 (별도 검토)

### 컴파일러 포팅
- 추상 I/O 인터페이스의 글 OS 구현
- 메모리 모델 차이 (글 OS의 영속 vs 통상 프로세스)
- 자체호스팅 고정점 — 글 OS 안에서 stage2 == stage3 확인
- ★ **이게 안 되면 MVP 실패**

### 글 OS 자체호스팅
- 글 OS의 ELF 빌드 절차가 글 OS 안에서 동작
- 새 ELF로 부팅해서 동일 환경 재현

## 위험과 폴백

### R-13 (★ 가장 큰 위험): 컴파일러 포팅 API 불일치
- 페이즈 4 후반부터 사전 대응 (spike-1, spike-2)
- 발생 시: 컴파일러 측 추상화 강화 또는 글 OS 측 호환 레이어
- 폴백: 컴파일러 일부 재작성 (1~2개월)

### 한글 입력 어려움
- 페이즈 1에서 한글 출력만 부분 해결. 입력은 더 어려움
- 페이즈 5에서 입력기 spike 별도
- 폴백: 영어만 입력, 한글은 외부에서 작성한 파일을 가져오는 방식 (작품성 손실)

### 자체호스팅 고정점 미수렴
- stage2 ≠ stage3 → 글 OS에서 컴파일러가 미세하게 다른 결과
- 원인: 메모리 정렬, 비결정적 자료구조 순회, 영속 모델의 부수효과
- 디버그: 두 바이너리 diff 분석
